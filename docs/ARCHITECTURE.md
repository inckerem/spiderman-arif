# SKYTHREAD Architecture

This document is the plan the code follows. It is written before the code and kept in sync with it.

## 1. Stack

- TypeScript (strict), Vite, three.js 0.186.1 (pinned), lil-gui (debug panel), Playwright 1.56.1 (tests, uses the preinstalled Chromium). The multiplayer game server runs on Node.js 22 with `ws` 8.18.3.
- No physics engine. A custom kinematic character controller runs against an analytic static collision world (boxes, vertical cylinders, ellipsoids, a terrain height function and water).
- Everything is generated at load time from a seed: geometry, textures (canvas 2D), sounds (WebAudio synthesis). The only file asset is `public/audio/theme.mp3`, fetched from the same origin.

## 2a. Maps

The game builds one map per page load; a map switch saves `settings.map` and reloads with `?harita=<id>` (other URL parameters such as `seed` stay). `Game` gets the id through `GameOptions.mapId` (`App.boot(seed, mapId)`), and every layout carries `layout.mapId`, so any code holding a layout reaches its map with `getMap(layout.mapId)` (simulation) or `getMapVisuals(layout.mapId)` (rendering) without new constructor parameters. Generic code (buildings, trees, props, traffic, pedestrians, the player) reads the generic layout fields; Manhattan-only data (avenues, streets, park rectangle, pond, islet, bridge spec) is read only inside `maps/manhattan/` and through the map hooks. A golden digest (`__game.goldenDigest()`, `tests/golden/manhattan.json`) hashes the Manhattan layout, the collider arrays and the outputs of the deterministic drivers; refactors that must not change behaviour are checked against it bit for bit.

### Istanbul (M13)

`maps/istanbul/` builds the second map in about 0.6 s: `data.ts` holds the compressed-real geography (land polygons, hills, hand-laid arterials, landmark sites, parks, piers, BSP roots), `terrain.ts` bakes the heights (hills faded in from the quay by an exact shore distance transform, then slope-limited), `streets.ts` the street tools, `gen.ts` the layout:

1. Coastal roads are the 22 m iso line (marching squares) of the distance to water or to a coastal landmark site, so they follow the shore and go around Dolmabahçe or Ortaköy on the inland side.
2. Hand-laid axis-aligned arterials (Atatürk Bulvarı, Divanyolu, Tarlabaşı, Cumhuriyet-Büyükdere, Barbaros...) are clipped where they would cross water, a landmark site or a park.
3. A seeded BSP per landmass splits rectangles at 35-65 % (±6 m) into streets (11-14 m, cars) or lanes (6-8 m); an arterial crossing a cell over 40 % of its extent forces the cut. Cuts are clipped like the arterials, so streets end in T-junctions at landmarks and parks.
4. Each leaf keeps its largest rectangle of valid ground (on land, clear of the coastal road, landmark sites, parks and every road strip) as a block. Lots of 10-22 m (Levent 30-48 m) get plain box buildings (4.0 m shop floor, 3.1 m floors, district floor ranges) on a stone plinth from below the low side up to the highest ground plus the curb; lots that span more than 6 m of height are split.
5. Blocks, landmark sites and parks are raised by the curb (`RectIndex`); everything else (roads, quays) is at the road level, so the ground mesh and the physics agree.

Landmarks and bridges (`maps/istanbul/landmarks.ts`) are lists of parts (`maps/common/prims.ts`: boxes, vertical cylinders, ellipsoids, drawn-only tubes and collide-only cable pieces). The same list feeds `addColliders` and the greybox geometry (`maps/common/partsGeo.ts`, merged into the chunk prop builders), so collision and visuals agree by construction. Helpers build domes (ellipsoid on a drum), minarets (pedestal box, shaft, standable şerefe rings, stacked-cylinder cap), round towers, cones as stacked cylinders, and cable chains (thin boxes for segments in an X or Z plane, at least 0.25 m half thickness and at most 0.5 m of rise per box; vertical cylinders otherwise). Every structure stands on its own stone plinth at the highest ground under it. Landmark colliders are owned by ids from 200000 up (buildings use their index, trees 100000 up). The generator keeps trees and lamps out of the part footprints.

Its ground (`world/render/terrainGeo.ts`) is a 4 m terrain grid (water vertices next to land pulled onto the shore line), slabs draped at the curb height for blocks, plazas and parks, road ribbons as decals, seawalls along the polygon edges, and piers.

## 3. Fixed-timestep loop

- Simulation rate 120 Hz (`dt = 1/120`). `requestAnimationFrame` feeds an accumulator with the clamped frame delta (max 0.1 s). While `acc >= dt`, the previous state is snapshotted and one tick runs. At most 12 ticks per frame; excess time is dropped (slow motion instead of a spiral of death).
- Rendering interpolates the player transform between the last two ticks with `alpha = acc / dt`. The camera is evaluated per frame from the interpolated position; mouse look is applied per frame (zero added latency) and the yaw/pitch are latched into each tick's input snapshot.
- Input edges (presses/releases) are queued and consumed by the next tick, so a click shorter than a frame is never lost.
- Test mode (`__game.setManual(true)`) stops the real-time accumulator; tests call `step(n)` which runs exactly `n` ticks. Same code path, deterministic for a given seed and input script.

## 4. Collision approach

### 4.1 Static world

All static colliders are analytic primitives stored in typed arrays:

- **Box** (axis-aligned): building tiers, parapets, podiums, rooftop HVAC, piers, bridge deck and towers, benches, parked cars, park walls, railings.
- **Vertical cylinder**: tree trunks, lamp posts, hydrants, antennas, water tanks, bridge pylons.
- **Ellipsoid** (vertical axis of revolution): tree canopies.
- **Terrain**: a height function behind the `TerrainModel` interface (`physics/terrain.ts`), not geometry. `baseHeight(x, z)` is the road level and `height(x, z)` the walkable ground (road level on roads, plus the 0.15 m curb elsewhere). `FlatGridTerrain` (Manhattan) has roads at y = 0, blocks (sidewalks, plazas, park) at y = 0.15 and the water surface at y = -1.2 outside the island and in the pond. The raycast asks the terrain for its own hit (`rayIntersect`, which also reports water and the surface normal) and the water respawn asks it for the nearest dry spot (`nearestLand`). Height checks in targeting and the autopilot use the altitude above `baseHeight`, which is the absolute height on the flat map. `HeightfieldTerrain` (`physics/heightfield.ts`, Istanbul) bakes the road level on a 2 m grid (bilinear) with a 16 m max mip; water is everything outside the land polygons (`physics/waterMask.ts`: 16 m buckets that are land, water or mixed, and mixed cells decide exactly by counting edge crossings from a reference point kept clear of the cell's edges), and roads come from `physics/roadIndex.ts` (segments with a width, bucketed). Rays clip to the height slab down to the water level, skip 16 m cells whose maximum is below the ray, march 1 m steps in the others (0.1 m beside a quay wall) and bisect the way in 8 times; the water surface is hit where the ray meets the water level over water first. `__game.terrainSelfTest()` (test `terrain.spec.ts`) checks rays against a brute-force 5 cm march, the water mask against plain point-in-polygon, the road index against a plain scan, the slope limit and `nearestLand`.

Each collider carries flags: `anchorable`, `climbable` (building facades, bridge towers), `cameraBlocks` (false for thin props so the camera does not pop on lamp posts), surface type (concrete, metal, wood, grass, foliage, glass) for footsteps.

Buildings are made only of boxes whose visual surfaces match the collider within 0.3 m (cornices protrude at most 0.25 m, pilasters 0.12 m). Non-box crown shapes are built as stepped boxes so visual and proxy stay identical.

### 4.2 Spatial index

A uniform grid of 16 m cells covers the world. Each cell lists the collider ids overlapping it. Queries:

- `queryAabb` gathers candidates (deduplicated with a stamp counter).
- `raycast` walks the grid with Amanatides-Woo DDA and tests colliders cell by cell, stopping at the first confirmed hit.
- `sphereCast` is a raycast against colliders inflated by the radius (used by the camera).
- `capsuleOverlap` / `pointInside` power the fuzz checks and recovery.

### 4.3 Player capsule resolution

The player is an upright capsule (radius 0.38 m, height 1.8 m). Because it is always vertical, closest points against boxes and vertical cylinders are exact and cheap (XZ clamp plus Y interval overlap). Ellipsoids use a scaled-space radial projection, which is accurate for the near-spherical canopies.

Per tick:

1. Candidates are gathered once for the AABB of the whole tick's sweep, expanded by the radius.
2. The tick is split into `n = ceil(|v| * dt / 0.15 m)` substeps, so a substep never moves more than 0.15 m. The thinnest collider is 0.24 m and the capsule radius is 0.38 m, so tunnelling is impossible up to any speed (at 100 m/s that is 6 substeps).
3. Each substep integrates, then runs up to 4 Gauss-Seidel iterations: push out along the contact normal by the penetration depth and remove only the velocity component into the surface (tangential velocity is kept, so glancing contacts never stall).
4. Terrain is resolved last (`y >= groundHeight`). Contacts are classified (ground if `n.y > 0.65`, wall if `|n.y| < 0.35`, ceiling if `n.y < -0.6`).

Kinematic moves (zip, vault, mantle) go through the same resolver; if a kinematic path is pushed off course or blocked, it aborts into the air state with the current velocity.

### 4.4 Safety nets

- Deep penetration (> 5 cm after resolution) for several ticks, or no progress for 3 s while the player is trying to move or is airborne, triggers recovery: search upward, then a ring search, for the nearest free capsule position with support below. The visual position blends to the new position over 0.35 s (render offset decay) so there is no jolt.
- Water: feet below the water surface → splash, then respawn at the nearest sidewalk or roof.
- World edge: beyond the soft boundary a smooth acceleration turns the player back toward the island; the hard clamp is never reached in practice.

## 5. Swing model

- Rope is an inequality constraint on the rope point (feet + 2.0 m): slack when closer than the rope length, taut otherwise. When taut: project the position onto the sphere and remove only outward radial velocity.
- Arcade layer: reduced gravity while taut, tangential force from input toward the camera direction, gentle heading steering that preserves speed, soft speed cap with drag above 60 m/s, catch conversion (when the rope snaps taut, most of the removed radial speed is redirected tangentially so falling into a swing never stalls), automatic ground clearance (the rope reels in so the arc bottom stays above ground), hands alternate, good-release window on the rising part of the arc with a launch bonus and a visible cue.
- Controls: pressing the left button fires a line at the crosshair target and the line holds while the button is down; while it is held with no usable point under the crosshair, the line fires as soon as one appears. Letting go (or Space) releases with a push forward and up (`cut.up`, `cut.forward` fading out at speed) that grows over the first `cut.fullAfter` seconds on the line, so a tap does not launch; a release inside the good-release window also gets the launch bonus. The right click starts the pull line, which eases in from `zip.startSpeed` to `zip.speed` and can be cut with Space the same way.
- Attach latency: a fired line reaches the anchor in at most 60 ms, so a release followed by a new press is attached again in well under 150 ms.
- Line of sight from the hand to the anchor is checked every tick; when blocked the rope releases gracefully (no push). If the button is still held, the line fires again as soon as the crosshair finds a usable point, like any held press.

## 6. Targeting

1. Ray from the camera through the crosshair. A hit within 120 m (swing) or 80 m (pull line) of the player on an anchorable surface, facing the player, with clear line of sight from the hand becomes the anchor; swing anchors must also be at least 4 m above the feet and 12 degrees above the hand, and not a roof top.
2. When that point is not usable, rays on two rings around the crosshair (half and full `aim.magnetismDeg`, 4 and 8 rays) try again, closest ring first, so building edges and thin trunks still catch. One set of rays fills both the swing and the pull-line target. Nothing usable means no line.
3. The result drives the reticle (valid anchor highlighted with a marker at the anchor, invalid dimmed).
4. The wide search (`Targeting.plan`) examines anchorable colliders within 72 m: for each it takes the closest surface point to an ideal point placed forward and upward along the view, scores candidates by angle, distance band, height gain and surface type, and line-of-sight checks the best few. Gameplay never uses it; the menu autopilot and the test bots use it to choose where to aim before they click, and test (c) uses it to measure anchor availability.

## 7. Rendering

- Cel shading: `MeshToonMaterial` with a 3-band gradient map, patched via `onBeforeCompile` for facade windows (shared window atlas texture plus per-window lit hash), wind sway (trees), and an extra MRT output with view-space normals.
- Outlines: post-process edge detection on the depth buffer (Laplacian of inverse depth, which is zero on planes so flat surfaces never produce false edges) and the normal buffer (creases), with distance fade to prevent shimmer. Works with instancing at no extra draw calls.
- Pipeline: shadow map (one directional light, texel-snapped around the player) → MRT scene pass (color, normal, depth) → composite pass (outlines, speed lines, grading) → FXAA → screen. Render scale and dynamic resolution resize the internal targets; a smaller internal image is upscaled with bilinear filtering (by the FXAA pass, or a plain copy pass without FXAA).
- Batching: facades, roof props, street props, signs and lamp bulbs are merged per 240 m chunk into one draw call (one shared cel material, per-vertex mode selects window/plain/emissive/sign shading); ground is merged likewise. Trees (near/far LOD), cars and pedestrians use `InstancedMesh`. The hero is one rigidly skinned mesh (one draw call). Chunks are frustum culled.
- Day-night: time drives sun/moon direction, light colors, hemisphere ambient, fog, sky shader, window emission (per-window thresholds so lights come on gradually), street lamp emission and light pools. A `storm` factor lays an overcast over any hour (grey sky and fog, nearer fog, dimmer sun, swollen low clouds, no sun, moon or stars) and `flash` adds lightning; `hold` lets the rooftop moment drive the hour.
- Rain (rooftop moment): one transparent mesh of camera-facing streaks built once at load; the vertex shader moves each streak along the fall velocity and wraps it into a 38 x 30 x 38 m box around the camera, so a frame only sets a few uniforms. It writes no depth and leaves the normal buffer alone (no outlines). The composite pass adds the rainy mood grade (cooler, darker, more contrast and vignette) and lightning as uniforms of the existing program.

## 7a. Attract mode and rooftop moment

- Attract mode: in the menu view the loop ticks a second `Player` (the real simulation, separate from the game's player, so nothing it does reaches play and manual test mode never runs it) with input from the `Autopilot`, aimed through its own unrendered `CameraRig`. Each frame the hero mesh is posed from it by a second animator and the director places the game camera. Play from the main menu resets the game's hero to the spawn roof with a fresh camera; returning to the main menu resumes the attract hero where it was.
- Rooftop moment: `App` updates it every frame with `live` = playing with the pointer locked. Arming needs 20 s of play and some movement (5 m or a line) since the last spawn, respawn or new game, then the hero grounded on a building roof at least 8 m above the street, still, no input held or pressed and no ring race; after 5 s it restarts the music from the top of the track, tweens the hour through dusk to night (4 s), brings rain, overcast and the grade, lights the hero with a rim and fill, hides the HUD behind letterbox bars and blends the gameplay camera into a slow orbit (kept out of geometry by `clearShot`, turning back, rising or cutting when cramped). Line presses are dropped while the orbit shows. Input activity is counted by `Input` (keys except the music and photo keys, mouse buttons, wheel, touch, deliberate mouse travel); a change ends the moment and everything eases back to the saved hour, unless the player set the hour (hour keys, photo time slider, fast-forward), which then stays. Pause and photo mode hold it (a lightning flash goes out).

## 7b. Touch input layer

- Touch mode is decided once at start-up (`detectTouchMode`): a coarse primary pointer plus touch points (phones, tablets), or `?dokunmatik=1`/`=0`. A laptop with a touchscreen has a fine primary pointer and stays on mouse and keyboard. `App.touchMode` picks the flow, `UI` the texts and layout (root class `sk-is-touch`), and `TouchControls` (`input/touch.ts`) is created only in touch mode.
- `TouchControls` is one DOM layer between the HUD and the photo panel/menus: a stick zone (left 42 %), a look zone (the rest), the button pad (bottom right, laid out in units of `clamp(48px, 14.5vh, 74px)` from the safe-area corner) and the pause button (top left). Pointer Events with `setPointerCapture` and per-pointer ids: one finger owns the stick, one the look drag, one each button, so any combination works at once. Buttons release on `pointerup`, `pointercancel` or `lostpointercapture`.
- Everything writes into `Input`, so the simulation sees one input path: buttons call `pressVirtual(action)`/`releaseVirtual(action)`, which hold the bound action with the same latched press/release edges as keys (a tap between two ticks still reaches the tick as press plus release, the sub-frame click rule); the stick calls `setStick(x, y, rimSprint)`; look drags call `addLook`, which adds to the mouse deltas that `rig.applyMouse` consumes each frame (CSS px times `touch.lookRadPerPx` times the touch sensitivity, divided by the mouse factor, so invert Y and the pitch limits apply unchanged); reel buttons add wheel notches (repeating while held).
- `TickInput.moveX/moveY` are analog: keys give exactly -1, 0 or +1 (plus the stick axes, clamped), and `Player` already scales by the wish length (ground target speed, air control, swing pump and steer, wall crawl), so a half push runs at half speed. The stick has a dead zone (0.12 of its travel), reaches 1 at 0.88 and sets `TickInput.groundSprint` at the rim (0.97): sprint speed on the ground only. `sprint` (Shift, the Tırman button) keeps its wall-cling meaning, so a fully pushed stick never clings to or drops off walls by itself.
- The DOM is touched only on pointer events (knob transform, written when the rounded offset changes; the base moves under the thumb once per touch) and on view changes (`setView('play' | 'photo' | 'off')`, `setSwinging` for the reel buttons, both guarded); the per-frame `update` only counts down reel repeats. Nothing is allocated per frame.
- Flow: on touch, `lockForPlay` starts play at once (input enabled, no pointer lock) and asks for fullscreen plus a landscape orientation lock (Android; failures ignored). Pause comes from the pause button, a hidden page (`visibilitychange`) or an upright device (`resize`/`orientationchange`/`screen.orientation` change: the Screen Orientation API says portrait and the view is more than 1.2 x taller than wide, or without the API the view shape alone; a landscape device in a tall Split View window never counts) shows the rotate prompt above everything and pauses; Oyna or Devam Et in portrait pause again, and "Yine de oyna" dismisses the prompt until the device turns to landscape. Photo mode and the music toggle are pause-menu buttons on touch; in photo mode the layer shows only the stick (flies the camera) and the look drag. Audio unlock is retried on `pointerup`/`touchend`, the events that grant activation on iOS.
- Aim: `Targeting.touchAim` widens the crosshair magnetism ring to `aim.touchMagnetismDeg` (4 degrees instead of 2.5).
- Settings: `touchSensitivity` (0.2-3); with nothing stored yet a touch device starts on Low quality (`loadSettings(firstRun)`), and "Varsayılanlara dön" restores Low there. The settings screen shows the touch sensitivity instead of the mouse's and no key-binding row; the controls screen shows the touch layout card. The `Saldırı` (Attack) button shows while combat runs: `App` calls `TouchControls.setAttackHandler({ press, release })`, which turns its press/release into `attack`/`attackPressed` (F) and a 0.4 s hold into `finisherPressed` (E).

## 7c. Combat client (M11)

- `combat/client/link.ts`: `CombatLink`, the client side of a combat room (shaped like the design's `RoomLink`, which M12 extends with the remote-hero roster): `now()` (room time, what intents are stamped with), `renderTime()` (`now()` minus the render delay), `tick(dt, heroState)` every 120 Hz tick (upload the hero, advance or poll the room, deliver messages), `intent(i)`, `setPaused`, `close`, and the `view`. Down messages are the protocol's shapes in object form: `ce` event batches and `snap` enemy snapshots (`EnemySnap` per enemy, the 0x03 entry before quantization, plus `SelfSnap`, the receiving hero's health, down state, combo, focus and i-frames). M12's network link (de)serializes exactly these and aligns them with `src/net/protocol.ts`.
- `combat/client/localLink.ts`: `LocalCombatLink`, single player. It owns no extra state: each tick it writes the hero's `HeroState` straight into the `CombatSim` (pid 1), accumulates time and steps the sim at 30 Hz (every 4th 120 Hz tick, so manual stepping stays deterministic), then hands the step's events and a pooled snapshot to the view with no serialization. Intents go to `CombatSim.intent`, so single player runs the server's validation. Render delay: one combat tick.
- `combat/client/combatView.ts`: `CombatView`, what the client knows: `enemies` (`ViewEnemy`: replicated fields plus an 8-sample ring per enemy, interpolated in position and yaw at the render time, extrapolated at most 0.15 s on an underrun, snapped on a change into YANKED or KO; render-only `flinchUntil` for predicted hits), `self` (from snapshots and `hit`/`down`/`respawn` events), `threat` (the soonest `tele` aimed at this hero until it lands, misses or passes), a queue of received events (`drainEvents`) and a short log for tests.
- `combat/client/heroState.ts`: `fillHeroState(player, afk, out)`.
- `combat/client/heroCombat.ts`: `HeroCombat`, the hero's side. `route(inp, dt)` runs on the `TickInput` after `fillAim` and before `player.step`; it implements the routing rules of the design (§4 there, recorded in DECISIONS): it captures whole left-button gestures that start on a target (the swing fields read false until the button is up, so no line fires and a button-held line can never be cut by the capture), right-button gestures on an enemy (tap = yank, hold `pinHold` = pin), Space while an attack on the hero is due (dodge; held Space stays masked), F (`attack`: always a strike, auto-target) and E (`finisher`: takedown); while the hero is knocked out it zeroes all input. It only decides: the player changes in `after(events)`, after the step (lunge, strike, dodge, takedown, buffered next strike), so every player event it causes reaches the game's event loop in the same tick. `after` also handles the step's `lungeEnd` (strike on arrival) and `strike` contact frames: in reach of the view's interpolated target it plays a render-only flinch (`CombatView.flinch`) and sends the intent stamped with the render time and the hero position; damage, KO and the combo come back as confirmed events. `onEvent` applies the room's events to the hero (`hit` → `Player.applyHit`, `down`/`respawn` → `Player.setDown`). `pick` and `pickLine` are the target pickers (downed within 3 m, close range in the front 220°, crosshair cone with line of sight, free-flow around the stick direction during a combo or when engaged on the ground, and for F the nearest enemy in view). `hud` (combo, focus, target, threat) feeds the chunk 7 HUD.
- `Player` (M11): `MODE_STRIKE` (`MODE_NAMES` 'strike') with `strike.kind` lunge, hit or dodge, moved kinematically through the capsule resolver like zip: `beginLunge(tx, ty, tz, stop, air)` (lets go of a line with no push, 24 m/s until `stop` from the target, aborts like zip when it stalls against geometry, `lungeEnd {ok}`), `retargetLunge` (homing), `beginStrike(move, action, contact, dur, fx, fz)` (faces the target, a small step forward on the ground or a hang at reduced gravity in the air, `strike {move}` at the contact time), `beginDodge(dx, dz, air)` (a sidestep on the ground; in the air or on a line only the animation), `applyHit` (knockback and a flinch; interrupts a combat move), `setDown` (lines cut, lies there; `down`/`revive` events), `playCombatAnim`, `clearCombat`. `combatAnim {action, t0, dur, side}` (actions in `CA`) is what the animator's overlay plays; `cameraMode` maps a combat move to ground or air for the camera rig.
- `character/animSource.ts`: `AnimSource`, the animator's whole view of a hero (mode, velocity, facing, dive, roll, grounded, surface, collision world, a clock, rope, zip, wall and traverse fields, `combatAnim`, `groundBelow`). `Player` satisfies it structurally; M12's remote heroes implement it from replicated state, so the same animator poses them. `CharacterAnimator(rig, src: AnimSource)`.
- Animator combat: `S_COMBAT` for MODE_STRIKE (guard arms; planted IK feet when grounded, a dash pose for the lunge, gathered legs for a dodge step or an air strike) and an overlay applied after the state blend and before limb collision, weighted in over 0.06 s and out over 0.12 s after the action's length: jab and cross extend one arm with a chest twist, the kick chambers and extends one leg, the uppercut (and the two-handed takedown) rises from a crouch, the air strike splits the legs, the ground finisher punches down, yank reaches and hauls back, pin shoots both hands, the dodge gathers the legs and rolls the body to the side, a hit rocks the torso back, and knocked out the whole body falls flat (root pitched back, pelvis at 0.22 m) and gets up again on revive.
- Touch: `App` sets the `Saldırı` handler while combat runs (`TouchControls.setAttackHandler`): a press is `attack` (F), holding it 0.4 s also sends `finisher` (E).
- `combat/render/debugCapsules.ts`: temporary enemy visuals until the chunk 5 rigs: one `InstancedMesh` of capsules sized by kind, coloured by kind and tinted by state (one draw call).
- `Game` builds the spawn points, the `CombatSim` (seeded from the city seed, 30 enemies), the view, the local link and the capsules at load. `simulate` runs `input.sample → injectInput → fillAim → heroCombat.route → player.step → heroCombat.after → stepCombat → player events` while `combatEnabled` (`stepCombat`: link tick, view update at the render time, then the received events: a `respawn` of this hero teleports the player, `heroCombat.onEvent` applies hits and down state, and everything goes to `onCombatEvent`). A new game resets the room. Manual test mode (`setManual(true)`) turns combat off and the scheduler and roaming flags off; `__game.combat.*` turns it on and drives it (`enable`, `spawn`, `spawnAhead`, `arenaSpots`, `enemies`, `simEnemies`, `clear`, `setHp`, `killAll`, `stepSim`, `startEvent`, `setScheduler`, `state`, `aimAt`, `hero`) plus the in-page drivers of `debug/combatDrivers.ts` (`routingTest`, `comboTest`, `lineTest`, `dodgeTest`).

## 8. Performance budget

| Item | Budget | Plan |
| --- | --- | --- |
| Draw calls | ≤ 600 | ~150-250 typical (chunks, instancing, one-mesh character) |
| Visible triangles | ≤ 2 M | boxes plus textures for detail, low-poly instanced props |
| Simulation | ≤ 1 ms per tick | grid queries, analytic primitives, targeting at 60 Hz |
| Cold load | < 10 s | city generation < 2 s, shaders compiled during loading |
| Frame hitches | none > 40 ms | no allocation in hot loops, precompiled shaders, no runtime geometry rebuilds |

Dynamic resolution follows the cost the resolution can change, not the frame interval (which never drops below 16.7 ms on a vsync-locked 60 Hz display): the GPU time of the passes where `EXT_disjoint_timer_query_webgl2` delivers samples, otherwise the CPU time of the render call plus, for clearly late frames, the frame interval minus the previous frame's CPU work outside rendering. Simulation, traffic, crowd and animation time are left out. It lowers the internal render scale (floor: 0.75 x the CSS pixels, so 0.5 at pixel ratio 1.5) when the cost exceeds 90 % of the 16.7 ms budget and raises it back below 60 %, with hysteresis and a hold after raises that had to be undone that doubles up to 30 s and resets after a minute without a drop. The GPU timer falls back to the CPU cost after a second without samples, drops stuck queries, discards results across disjoint events and is rebuilt on WebGL context restore.

## 10. Multiplayer server (M12)

Design: `docs/design/m11-m12-combat-multiplayer.md` (M12). Movement is client-authoritative (each client simulates its own hero at 120 Hz and uploads it at 20 Hz); combat, crime events, health and the day-night clock are server-authoritative.

```
server/main.ts         entry (dist-server/server.mjs): config, start, SIGTERM/SIGINT graceful stop
server/app.ts          one http.Server: GET /healthz, static dist/, WebSocket upgrade on */ws (origin check,
                       connections per IP), 30 Hz drift-corrected loop over all rooms, 20 s ping heartbeat
server/config.ts       env vars (PORT, MAX_PLAYERS_PER_ROOM, ...) with the same names as --flags
server/roomManager.ts  public rooms per map (#1, overflow #2, ...), private rooms by 6-character code,
                       reconnect tokens, pid → connection routing, room cleanup
server/session.ts      one socket: hello within 5 s, token buckets, garbage/flood kicks, leave/close handling
server/limits.ts       token bucket, sustained-abuse meter, connections per IP, client address (X-Forwarded-For)
server/static.ts       MIME map, traversal guard, cache headers (index.html no-cache, assets/* immutable)
server/mapRuntime.ts   per-map layout, collision world and combat spawn points, built once and shared by rooms
```

- **Build:** `vite build --config vite.server.config.ts` (an SSR build with rolldown) bundles `server/` and the shared `src/` modules (three tree-shaken in, `ws` external) into one `dist-server/server.mjs`; `tsconfig.server.json` type-checks it without DOM types.
- **Protocol** (`net/protocol.ts`, `net/codec.ts`, version 1): JSON text frames for control and combat events, little-endian binary frames for high-rate state: 0x01 own hero state (34 B at rest, 46 B on a line, plus events), 0x02 the relay batch (`u8 pid` + the sender's own body, its time clamped by the server), 0x03 enemy snapshot (18 B per enemy, 30 nearest within 300 m, 15 Hz). Messages over 4 KB close the socket (1009); malformed ones close it (1008).
- **Room** (`sim/room.ts`): `admit` (name check, `#2` suffix, capacity, reconnect by token), `drop` (keep the slot for the 30 s grace, the hero frozen and `afk`, or remove it), `onState` (time clamp into [receive − 1 s, receive], sanity check, `RoomSim.upsertHero`, queue for relay), `onIntent` (hero targets rejected outside PvP rooms, times converted to sim seconds), `step(nowMs)` at 30 Hz (grace expiry, shared clock with a broadcast every 5 s, `RoomSim.step` only while someone is connected, `ce` event batch, snapshots every 2nd step, one relay batch per recipient). The host passes its millisecond clock; JSON times are room seconds; the Room converts to and from sim seconds.
- **Movement sanity:** NaN or out of bounds (map bounds ± 400 m, y in [−5, 900]) → `correct`. A move longer than 110 m/s × Δt + 2 m is accepted only with a changed teleport counter and a target within 80 m, at the map spawn or at the sim's respawn point; otherwise `correct` with the last valid position. States still in flight before the client applied a correction are dropped without counting; a correction not applied within 1.5 s is sent (and counted) again; more than 5 in 10 s is a kick.
- **Combat hook:** `RoomSim` (`sim/types.ts`): `upsertHero`, `removeHero`, `intent`, `step` (exactly 1/30 s), `drainEvents`, `snapshot` (nearest first into preallocated `EnemySnap`s), `crimeEvents`, `heroHp`, `respawnPoint`, `debug`, `setRtt`, `enemyCount`. `sim/combatRoomSim.ts` implements it around M11's `CombatSim` (validation stays the sim's own); `server/mapRuntime.ts` builds the layout, collision world and spawn points once per map (about 1 s for Manhattan) and every room's sim shares them. `SIM=null` selects `NullSim` (presence only).
- **Load** (`npm run test:server:load`, `tests/serverLoad.load.ts`; Node 22 in a shared 4-core sandbox, bots in a separate process; bots walk and upload at 20 Hz, strike nearby enemies once a second and follow their respawns; enemies are kept at about 30 per room through the test hooks; detail from `/healthz?detail=1`, which exists only with `TEST_HOOKS=1`):

  | Scenario | Room step p50 / p95 / max | Whole tick p50 / p95 | Server CPU | RSS / heap | Down / up per client |
  | --- | --- | --- | --- | --- | --- |
  | 1 room, 16 players, 30 enemies, 60 s | 0.53 / 1.10 / 3.5 ms | 0.54 / 1.11 ms | 0.05 core | 111 / 23 MB | 19.1 / 0.7 KB/s |
  | 10 rooms, 160 players, 300 enemies, 30 s | 0.50 / 0.99 / 6.7 ms | 4.2 / 7.4 ms | 0.21 core | 116 / 27 MB | 20.0 / 0.7 KB/s |

  A full room costs about 2 % of a core (the design budget was ~6 %); the 33 ms tick has room for roughly 40 such rooms per core before the loop falls behind, so `MAX_ROOMS=200` needs about 5 cores at full occupancy. The download per client (~20 KB/s, about 160 kbit/s) matches the design estimate of ~23 KB/s; no bot was corrected or disconnected.
- **Deploy:** multi-stage `Dockerfile` (build stage runs `npm run build` and `npm run build:server`; the runtime stage has production dependencies, `dist/` and `dist-server/`, runs as `node`, `HEALTHCHECK` on `/healthz`), `docker-compose.yml` (port bound to 127.0.0.1:8080, read-only, `no-new-privileges`, 512 MB) and `deploy/nginx/skythread.conf` (TLS at Nginx, HTTP → HTTPS, WebSocket upgrade, one-hour proxy timeouts on `/ws`).

## 11. Launchers

`BASLAT-Windows.bat`, `BASLAT-Mac.command` and `BASLAT-Linux.sh` start the game from a fresh clone with nothing preinstalled. Each only finds a usable Node.js and hands over to `scripts/launch.mjs`, so the behaviour is the same everywhere:

- `scripts/check-node.cjs` accepts the running Node.js when it satisfies Vite 8 (^20.19 or >=22.12) and npm is present.
- Otherwise `scripts/install-node-windows.ps1` (Windows) or `scripts/bootstrap.sh` (macOS, Linux) downloads Node.js 22.23.3 for the machine's OS and CPU into `.tools/node` and checks it against a SHA-256 pinned in the script. It is used only for this project.
- `scripts/launch.mjs` runs `npm ci` when the lockfile, OS or CPU changed since the last install (stamp in `node_modules`), builds with the Vite API when the content hash of the build inputs changed (stamp in `dist`), serves `dist/` with `vite preview` on 127.0.0.1 (port 4173 or the next free one) and opens the default browser.
- `--sunucu` builds the game server bundle too (content-hash stamp in `dist-server`) and runs `dist-server/server.mjs` on 0.0.0.0 (port 4173 or the next free one) serving `dist/` and the `/ws` rooms instead of `vite preview`, and prints the machine's local network addresses for phones on the same network.
- `.github/workflows/launchers.yml` runs every launcher with `--check` on Windows, macOS and Linux (x64 and ARM64), once with the runner's Node.js and once with the portable download.
